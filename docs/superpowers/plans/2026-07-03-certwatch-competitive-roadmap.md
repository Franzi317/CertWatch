# CertWatch → Keyfactor Command Competitor: Master Implementation Plan

> **For agentic workers:** This is a master roadmap. Each phase below gets its own
> detailed plan (superpowers:writing-plans) at execution time, executed via
> superpowers:subagent-driven-development or superpowers:executing-plans.
> Do NOT attempt to execute this document directly.

**Goal:** Evolve CertWatch from a TLS visibility/alerting tool into a self-hosted
certificate lifecycle management (CLM) platform — discover, renew, deploy, govern —
viable as a Keyfactor Command alternative for a single organization.

**Architecture:** Keep FastAPI + React + PostgreSQL. Add a Postgres-backed job
queue and separate worker process (no Redis/Celery), an issuer-adapter layer
(ACME first, AD CS second), a lifecycle-order state machine, deployment
connectors, Entra ID SSO with RBAC, and envelope-encrypted secrets. Evolutionary,
not a rewrite: the existing scanner, alert engine, and inventory model are kept
and become the "verify" leg of the renewal loop.

**Tech Stack:** Python 3.13 / FastAPI / SQLAlchemy 2 / Alembic / PostgreSQL 16,
React 18 + Vite, `authlib` (Entra OIDC), `acme` (certbot's library), `cryptography`
(Fernet envelope encryption), APScheduler (tick only — execution moves to workers).

## Global Constraints (from user scope)

- **No multi-tenancy.** No `Tenant` entity, no tenant headers, no org scoping. Ever.
- **SSO is Entra ID only:** OIDC (OAuth2/OpenID Connect) primary, SAML only if a
  blocking requirement emerges. No generic-IdP abstraction layer.
- Single-organization deployment: one org implements and maintains it. HA is
  active-passive + documented restore, not clustered consensus.
- PostgreSQL is the only production datastore. No Redis, no message broker, no
  OpenSearch. Queue = Postgres `FOR UPDATE SKIP LOCKED`.
- SQLite remains supported for dev/test only.
- Python 3.11+ floor, 3.13 recommended (matches current README).
- All new mutation endpoints require auth + write to `AuditLog` with actor.
- Secrets are never returned in cleartext by any API (existing rule — extend to
  issuer/connector credentials).

## Current State (verified against source, 2026-07-03)

- `backend/app/` — 14 modules: `main.py` (all routes, ~580 lines), `models.py`
  (Target, ScanJob, Endpoint, Certificate, CertificateObservation, AlertEvent,
  NotificationChannel, SystemSetting, AuditLog), `scanner.py`, `scan_engine.py`,
  `scheduler.py` (APScheduler in-process), `alerts.py`, `notify.py`, `targets.py`,
  `config.py`, `db.py`, `schemas.py`, `serialize.py`, `status.py`.
- Auth: optional shared bearer token (`require_auth` in `main.py:83`). No users.
- No migrations — `init_db()` creates tables; schema changes currently require DB reset.
- Scan execution: background thread per job inside the API process.
- Tests: 7 files under `backend/tests/`, pytest.
- Frontend: 7 pages (Dashboard, Targets, Certificates, Endpoints, ScanJobs,
  Alerts, Settings) + shared `ui.tsx`, `api.ts`.

**What CertWatch is missing vs Command (research doc, single-org lens):**
issuance/renewal/revocation, issuer connectors, deployment to stores, real user
auth + RBAC, migrations, durable job execution, reporting/exports, secrets
encryption, backup/restore story, metrics. Multi-tenancy and MSP features are
explicitly out of scope and deleted from the research roadmap.

## Phase 0 — Foundation (~6–8 weeks)

Everything later depends on this. No product-visible features except login.

### 0.1 Alembic migrations
- Add `alembic` to `backend/requirements.txt`; `backend/alembic/` env wired to
  `app.models.Base.metadata` and `settings.database_url`.
- Baseline migration autogenerated from current models; `init_db()` becomes
  "run `alembic upgrade head`" in production, keeps `create_all` for SQLite tests.
- CI/docker-entrypoint runs migrations before app start.

### 0.2 Users, Entra OIDC, break-glass admin
- New entities in `models.py`: `User` (id, email, display_name, role, source
  `entra|local`, disabled, last_login_at), no separate Role table — role is an
  enum column: `admin | operator | viewer`. Single org does not need scoped
  permission bindings; add them only if a real requirement appears.
- `backend/app/auth.py`: Authlib OIDC against Entra
  (`https://login.microsoftonline.com/{tenant}/v2.0`), authorization-code flow,
  session cookie (signed, `itsdangerous` already comes with FastAPI's Starlette).
  Config: `CERTWATCH_ENTRA_TENANT_ID`, `CERTWATCH_ENTRA_CLIENT_ID`,
  `CERTWATCH_ENTRA_CLIENT_SECRET`. Optional group→role mapping via
  `CERTWATCH_ENTRA_ADMIN_GROUP` etc.
- Local break-glass admin: `CERTWATCH_ADMIN_PASSWORD_HASH` env var, login form
  fallback when Entra is down. No self-service local users.
- `require_auth` is replaced by `require_role(min_role)` dependency; existing
  static API key survives as a **service-account token** for API automation
  (maps to role `operator`).
- Frontend: login page, current-user chip, 401 → redirect to login.

### 0.3 Role enforcement + audit everywhere
- Every route in `main.py` gets `require_role`: GETs = viewer, mutations =
  operator, settings/channels/users = admin.
- `audit()` gains `actor` (from session) and is applied to every mutation,
  including alert ack/mute and scan start/cancel. `AuditLog` gains `actor`
  column + index on `created_at`.
- `GET /api/audit` endpoint (admin), UI page with filter by actor/entity/date.

### 0.4 Secrets encryption (`SecretRef` lite)
- Fernet envelope encryption with `CERTWATCH_MASTER_KEY`. Helper module
  `backend/app/secrets.py`: `encrypt(value) -> token`, `decrypt(token) -> value`.
- `NotificationChannel.config` secret fields stored encrypted; migration
  encrypts existing rows. Issuer/connector credentials (Phase 1) use the same
  helper from day one.
- ponytail: no Vault/KMS integration — env-var master key with documented
  rotation procedure. Add Azure Key Vault-backed master key only if the org
  requires it.

### 0.5 Durable job queue + worker split
- New table `WorkQueue` (id, kind `scan|renew|deploy|report`, payload JSON,
  status `queued|leased|done|failed`, lease_expires_at, attempts, last_error,
  priority, created_at). Claim via
  `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` — safe for N workers, zero new infra.
- New process: `python -m app.worker` — loop: claim job, execute (scan via
  existing `scan_engine`, later renew/deploy), heartbeat lease, record result.
- APScheduler stays in the API process but now **only enqueues** (scan ticks,
  alert evaluation tick, renewal tick later). `enqueue_scan` writes a
  WorkQueue row instead of spawning a thread.
- Docker Compose gains a `worker` service (same image, different command).
  Scale = `docker compose up --scale worker=3`.
- Degraded mode: if `CERTWATCH_EMBEDDED_WORKER=true` (default for dev/SQLite),
  API process runs a worker thread — keeps the one-container quickstart.

### 0.6 Metrics + structured health
- `prometheus-fastapi-instrumentator` for API metrics; custom gauges/counters:
  queue depth, scan success rate, certs expiring 7/30/90d, renewal
  success/failure (Phase 1), worker heartbeat age. `GET /metrics`.
- ponytail: no OpenTelemetry tracing yet — add when someone actually needs to
  trace a request.

**Phase 0 exit criteria:** login via Entra works; all routes role-guarded; all
mutations audited with actor; `alembic upgrade head` from empty DB and from a
pre-phase-0 DB both succeed; scans execute via worker process; `/metrics` live;
all existing tests pass plus new auth/queue tests.

## Phase 1 — Lifecycle MVP (~10–12 weeks)

Turns "visibility + alerting" into "visibility + renewal + deployment." This is
the phase that makes CertWatch a Command competitor rather than a scanner.

### 1.1 Issuer abstraction + ACME adapter
- Entities: `Issuer` (name, type `acme|adcs`, config JSON with encrypted
  credential fields, enabled, last_test_at, last_test_ok).
- `backend/app/issuers/` package: `base.py` defines the adapter protocol —
  `issue(csr, profile) -> IssuedCert`, `revoke(serial, reason)`,
  `test_connection()`. Two implementations only; no plugin registry until a
  third issuer type exists.
- ACME adapter (`acme` library from certbot): account key stored encrypted,
  HTTP-01 via a built-in challenge responder endpoint
  (`/.well-known/acme-challenge/`) plus DNS-01 with an Azure DNS hook (fits an
  Entra shop; other DNS providers later). Works against Let's Encrypt and any
  internal ACME CA (smallstep, EJBCA-CE) — one adapter covers public + private.
- AD CS adapter: submit CSR via certsrv web enrollment (`certsrv`-style HTTP)
  with a service account. This is the natural private CA for an Entra/AD org.
- `POST /api/issuers`, `POST /api/issuers/{id}/test`, UI page.

### 1.2 Managed certificates + renewal policy
- Entities:
  - `ManagedCertificate` — the *logical* cert CertWatch owns the lifecycle for:
    subject/SANs, key policy (alg, size), issuer_id, renewal_policy_id,
    current_certificate_id (FK to existing `Certificate`), state
    `active|renewing|error|retired`. The existing `Certificate` table remains
    the deduped observed-artifact store — do not merge them (research doc's key
    modeling point).
  - `RenewalPolicy` — renew_before_days, key policy, retry backoff,
    require_approval (bool), deployment verification on/off.
- Promotion flow: from any inventoried `Certificate`, UI action "Manage this
  certificate" → creates ManagedCertificate prefilled from the observed cert.
  This is the on-ramp that turns inventory into lifecycle — Keyfactor's core UX.

### 1.3 Lifecycle orders (state machine)
- Entity: `LifecycleOrder` — managed_certificate_id, action
  `issue|renew|revoke`, status `pending_approval|queued|issuing|deploying|
  verifying|complete|failed|rolled_back`, attempts, approvals (actor, at),
  error, correlation id, timestamps per transition (JSON log column).
- Orders execute on the Phase-0 worker via WorkQueue (`kind=renew`). Each step
  transition is committed — crash-safe resume by re-leasing.
- Renewal tick (scheduler): daily, finds ManagedCertificates whose
  `not_after - renew_before_days <= today`, creates orders (idempotent — skip
  if an open order exists).
- Approval gate: orders with `require_approval` sit in `pending_approval`;
  approve/reject endpoints (operator creates, **admin approves** — two-person
  rule for revoke and production deploys).
- `POST /api/lifecycle/orders`, `GET .../orders`, `POST .../orders/{id}/approve`.
  UI: Orders page with state timeline.

### 1.4 Deployment targets + local connectors
- Entities: `DeploymentTarget` — kind `file_pem|file_pfx|jks|iis`, connection
  (agent id later; Phase 1 = "local" i.e. the worker host or a UNC/SSH path),
  path/binding config, credentials encrypted, post_deploy_command (optional,
  e.g. `nginx -s reload`), linked managed_certificate_ids.
- Connectors in `backend/app/deploy/`: PEM writer (cert/chain/key files, perms),
  PKCS#12 writer (`cryptography` does PKCS#12 natively), JKS via PKCS#12
  (modern Java reads PKCS#12; write real JKS only if a consumer demands it —
  note this ceiling in code), IIS binding via PowerShell remoting
  (Windows shop; uses `Import-PfxCertificate` + `netsh http`/IIS cmdlets).
- **Post-deploy verification:** after deploy, enqueue a targeted scan of the
  affected endpoints with the existing scanner; order only reaches `complete`
  when the new fingerprint is observed live. On mismatch → `failed`, keep old
  files (write-new-then-swap), alert. This closes the loop Keyfactor sells as
  "zero-touch" and reuses CertWatch's existing strength.

### 1.5 Lifecycle alerting + dashboard
- New alert rule types: `renewal_failed`, `deploy_failed`, `order_stuck`
  (reuses existing AlertEvent/dispatch machinery unchanged).
- Dashboard adds: managed vs unmanaged cert counts, renewal success rate (30d),
  orders in flight / pending approval.

**Phase 1 exit criteria:** a cert can be promoted to managed, auto-renews via
ACME against a test CA (pebble in CI), deploys to a PEM + PFX target, is
verified live by scan, and failure at any step alerts. AD CS adapter tested
against a lab CA. All order transitions audited.

## Phase 2 — Enterprise Controls (~6–8 weeks)

Makes it pass an internal security review and an ops handoff.

### 2.1 Reporting + exports
- CSV export on certificates/endpoints/orders list endpoints (`?format=csv`,
  same filters). ponytail: no report-builder engine — saved filters + CSV +
  scheduled email covers the real need.
- Scheduled reports: `ReportSchedule` entity (filter params, recipients,
  cadence) executed by worker (`kind=report`), delivered via existing SMTP
  channel machinery.
- Audit evidence export: date-ranged audit CSV (admin).

### 2.2 Outbound webhook events
- Emit events (cert discovered/changed, order state changes, alert raised) to
  the existing generic-webhook channel type with HMAC signature header.
  `GET /api/events` backed by a small `Event` table (ring-buffer style,
  90-day retention job).

### 2.3 Backup / restore / DR
- `scripts/backup.sh` + docs: `pg_dump` + master-key escrow note; restore
  runbook; `POST /api/admin/restore-check` verifying schema version + row
  counts + decrypt-ability of one secret (proves master key matches backup).
- Documented active-passive HA: 2× API + N workers against one Postgres;
  SKIP LOCKED already makes workers safe; APScheduler tick guarded by a
  Postgres advisory lock so only one API instance enqueues.

### 2.4 Findings (cheap crypto-risk win)
- `Finding` entity: rule id, severity, certificate/endpoint ref, first/last
  seen, disposition `open|accepted|resolved`. Rules run at scan time from data
  **already captured** in `Certificate`: key < 2048 RSA, SHA-1 signature,
  expired > N days, cert lifetime > 398d, self-signed in prod environment,
  deprecated TLS handshake alerts (only fields the scanner already returns).
- Dashboard: open findings by severity; Findings page with disposition flow.
- ponytail: this is Keyfactor's "risk analytics" slice at 5% of the cost
  because the scanner already collects the inputs. Protocol/cipher scanning
  (needs handshake enumeration) is deferred to Phase 4.

**Phase 2 exit criteria:** scheduled CSV reports arrive by email; webhook
events signed and documented; restore drill executed successfully from runbook
alone; findings visible on dashboard; security review checklist (auth, RBAC,
audit, secrets, backup) fully green.

## Phase 3 — Remote Agent + Store Connectors (~8–10 weeks)

Only phase that adds a new deployable. Do not start until Phase 1 connectors
have real usage — actual store demand should pick the connector order.

### 3.1 Remote orchestrator agent
- Python agent (same language as codebase — a Go rewrite is justified only if
  binary distribution becomes a real pain; note as explicit ceiling), installed
  as a Windows service / systemd unit on hosts the server can't reach.
- Enrollment: one-time token → agent gets a client cert (issued by CertWatch's
  own ACME/AD CS path — dogfooding); mTLS thereafter. Heartbeat + capability
  report to `POST /api/connectors/{id}/heartbeat`.
- Agent executes deploy jobs pulled from the server (outbound-only connection —
  firewall-friendly), reusing the exact Phase-1 connector code as a library.
- `ConnectorInstance` entity: name, host, version, capabilities, last_heartbeat,
  status. Connector health page in UI.

### 3.2 Store connectors, demand-ordered
- Candidates: Kubernetes TLS secrets (via kubeconfig/service account), Nginx/
  Apache (PEM + reload command — mostly already covered by file_pem +
  post_deploy_command), Azure Key Vault **deployment** (import cert to vault;
  Entra creds already configured for SSO), F5/load balancer if the org has one.
- Each connector = one module in the shared connector library + one
  DeploymentTarget kind + tests against a containerized fake where possible.

**Phase 3 exit criteria:** agent enrolls with mTLS, survives restart, deploys
to a host unreachable from the server, and shows health in UI; at least two
new store kinds shipped based on actual demand.

## Phase 4 — Selective Crypto Inventory (~8+ weeks, optional/on-demand)

The AgileSec slice. Enter only when Phases 0–2 are stable in production.
Priority order for an Entra shop:

1. **Azure Key Vault inventory** — enumerate certs/keys in vaults via Entra
   service principal; feed into existing Certificate/Finding models with a new
   `source` discriminator (`network|keyvault|repo`).
2. **Protocol/cipher analytics** — extend scanner to enumerate TLS versions/
   ciphers per endpoint (bounded handshake attempts); findings rules for
   TLS 1.0/1.1, weak suites.
3. **Repo scanning** — scheduled scan of configured Git repos (Azure DevOps/
   GitHub) for private keys, PKCS#12/JKS files, PEM blocks → findings.
4. PKCS#11/HSM inventory — only if the org actually owns HSMs.

## Explicitly Dropped from the Research Roadmap (single-org scope)

| Research item | Disposition |
|---|---|
| Multi-tenancy, `Tenant` entity, tenant headers | Dropped per user constraint |
| Generic OIDC/SAML multi-IdP support | Entra only; SAML deferred unless required |
| Go remote agent | Python agent; Go only if distribution pain proves real |
| Redis/broker-backed queue, Temporal-style workflow engine | Postgres SKIP LOCKED + state-machine table |
| OpenSearch/analytics index | Postgres (+ materialized views if dashboards slow) |
| SCEP / EST protocol endpoints | Deferred indefinitely — device enrollment is not the wedge |
| Connector SDK for third parties | Internal connector library only — no external ecosystem for a single org |
| Compliance framework mapping, SBOM/signed releases | Internal deployment; revisit only if productized commercially |
| Full HA (clustered, load-balanced, job-locked) | Active-passive + N workers + restore drill |

## Sequencing & Effort Summary

| Phase | Duration | Depends on | Headline |
|---|---|---|---|
| 0 Foundation | 6–8 wk | — | Migrations, Entra SSO, RBAC, audit, secrets, worker queue, metrics |
| 1 Lifecycle MVP | 10–12 wk | 0 | ACME + AD CS issuance, renewal orders, PEM/PFX/JKS/IIS deploy, verify loop |
| 2 Enterprise controls | 6–8 wk | 0 (parallel w/ late 1) | Reports, webhooks, backup/DR, findings |
| 3 Agent + connectors | 8–10 wk | 1 | Remote agent, demand-driven store connectors |
| 4 Crypto inventory | 8+ wk | 2 | Key Vault, cipher analytics, repo scan |

Roughly 9–12 months with 2–3 engineers to end of Phase 3 — the point at which
CertWatch covers the Command capabilities a single org actually exercises
(discover → renew → deploy → verify → govern). Phase 4 is pull-based.
